# codex-oracle 1.18 — "oracle daemon" design (for architecture review)

## Problem (measured, 2026-08-31, Claude Code 2.1.251 / codex-cli 0.151.0)
- A codex-oracle call is an MCP tool call; Claude Code moves it to a background "MCP task" after ~2 min, whose panel shows only status/elapsed. Progress notifications are request-scoped (token deregistered at backgrounding); MCP logging is deprecated (protocol 2026-07-28); MCP Tasks (SEP-1686/2663) are not supported by this client. Live output is only visible via a separate `tail -F` shell or an on-demand tool.
- `/mcp` reconnect / plugin reload / session exit sends the server SIGINT then SIGTERM (~100 ms); 1.17.x made runs survive via a file-backed spool + detach-on-shutdown + a /bin/sh watchdog + adoption, plus pid+start-time identity, claims, owned locks. It works (E2E on the real CLI) but it is a lot of machinery around a child that the server does not supervise (no exit code), and every review round finds a new edge.
- Background Bash shells stream stdout live in the Shells panel, write an output file, and deliver a native completion notification — but a background shell does not outlive Claude Code either.
- Spike results on `codex app-server` 0.151.0 (raw JSON-RPC from Python): per-thread pin (`model gpt-5.6-sol`, `reasoningEffort max`, `sandbox read-only`, `approvalPolicy never`) stored on the thread; event stream far richer than `exec --json` (message deltas, item events, `thread/tokenUsage/updated`, `account/rateLimits/updated`, `thread/status/changed`, `turn/completed`); when the STDIO client dies mid-turn the app-server exits and the turn is `turn_aborted`; `thread/resume` in a new process works and the model knows the prior turn was interrupted; over the unix-socket transport a second client can `thread/resume` a LOADED thread mid-turn and keeps receiving events after the first client disconnects — but OpenAI labels websocket/unix transport "experimental / unsupported"; version-exact schemas via `codex app-server generate-json-schema`.

## Requirements (unchanged product laws)
Pinned model + effort (never a fallback model); blind dispatch with an anchoring lint that can BLOCK; per-run journal + resume of the codex thread with original context; runs outlive the caller process (reconnect/reload/session exit) and are collectable; bounded output into the model context with the full answer on disk; push gate reads `tool:code_review | status:ok | tree:<dispatch digest>`; write mode (abraham) is SEALED (no network, no user MCP servers, workspace-write, one writer per tree, never auto-retried); macOS primary, Windows secondary; no experimental transport on the critical path.

## Proposed architecture
1. `oracle_core.py` (shared library, no MCP import): request envelope (JSON: kind ∈ review|architect|research|query|abraham, prompt fields, caller_hypothesis, web_search, infra, images, cwd, model/effort pin with env override), anchoring lint, prompt assembly (ADVISOR_CONTEXT.md injection, independence preamble, capability hunt), answer rendering (header signature with the DISPATCH-time tree digest), journal (append-only `runs.jsonl` folded by run id, run ids with random token), transient classification (overload vs disconnect) and backoff policy, output cap, tree digest, process identity (pid + start time), owned locks/claims.
2. `oracle_daemon.py` — ONE detached worker per user (`$CODEX_HOME/codex-oracle/` state dir; lock file with identity; lazily started by any front-end; exits after configurable idle). It OWNS `codex app-server` over STDIO (supported transport) as its child: restarts it on crash, checks the generated schema hash against the pinned version at start (drift = refuse + loud message). Per run it: creates a thread with the pin (`thread/start` model/effort/sandbox/approvalPolicy never), starts the turn, digests notifications into a per-run event log (`runs/<id>/events.jsonl` + human `live.log`), enforces the run deadline (`turn/interrupt` → status timeout), retries capacity/disconnect classes by starting a continuation turn on the same thread after backoff (pin never changes), writes `result.txt` + journal `end` (status earned by `turn/completed` status + final agentMessage), answers approval requests with a decline (policy never). Control plane = FILES in the state dir (request drop → daemon picks up; `cancel` marker → `turn/interrupt`; status = journal), so no custom socket protocol and Windows-compatible; the daemon polls the queue dir (or inotify/kqueue when cheap).
3. Front-end A — `oracle` CLI (`plugins/codex-oracle/oracle.py`): `review|architect|research|query|abraham` (validate envelope → lint → submit → FOLLOW: tail the run's live.log to stdout so Claude Code's background Bash streams it in the Shells panel → exit with the capped answer + result path; a Ctrl+C/TaskStop kills only the follower), plus `runs|log|collect <id>|cancel <id>|resume <id>`. Claude Code's native completion notification delivers the outcome.
4. Front-end B — thin MCP façade (existing server.py shrunk): tools become `start` (returns run id immediately), `status/log`, `collect(run, wait)`, `cancel`, `resume`; no tool holds a 60-minute request; existing tool names kept as compatibility shims that start+collect.
5. Hooks: PreToolUse on Bash commands invoking `oracle …` → parse the envelope path from the argv, run the anchoring lint → `permissionDecision: deny` with the finding (configurable to warn); keep the MCP nudge; push gate unchanged.
6. Abraham (write mode): the app-server instance loads user config (MCP servers, network); a sealed write turn needs `--ignore-user-config`-equivalent isolation. Options: (a) a second app-server child launched with `-c`/flags that seal it, if app-server supports `--ignore-user-config` and `mcp_servers` replacement (the `-c mcp_servers={}` deep-merge no-op is a known trap on 0.144); (b) keep abraham on sealed `codex exec` inside the daemon (proven). Default to (b) until (a) is measured.
7. Fallback: if the app-server contract breaks in a codex update (schema hash mismatch, missing methods), the daemon falls back to `codex exec --json` per run with the 1.17.x spool logic — same front-ends, same files.

## Open questions for the review
- Is a per-user daemon (vs per-workspace) the right unit? Cross-workspace journal scoping must stay (a run is only visible from its workspace or below).
- File-based control vs a unix socket the daemon owns (not codex's experimental one).
- How app-server surfaces provider capacity errors (`turn/completed` status? error items?) — must be measured before the classifier is ported.
- Daemon lifetime/idle exit vs warm app-server benefits; memory of a long-lived app-server with many threads (`thread/unsubscribe` unloads after 30 min idle).
- Windows: detached daemon via CREATE_NEW_PROCESS_GROUP|DETACHED_PROCESS; identity via process handles; no `os.kill(pid, 0)`.
